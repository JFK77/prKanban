6. MIGRATION RISKS (PRIORITIZED)
================================================================================

🔴 CRITICAL RISKS:

  1. Firebase Deeply Integrated
     • 14+ Firebase SDK calls scattered throughout code
     • Every CRUD operation depends on Firestore
     • Authentication completely Firebase-dependent
     • Impact: Must build complete REST API abstraction layer
     • Effort: 30-50 hours

  2. Monolithic File Architecture
     • 135 KB single HTML file with ~5000 lines embedded
     • Difficult to refactor and modularize
     • No build pipeline or module system
     • Impact: Harder to maintain and test
     • Solution: Split into modules, consider build system
     • Effort: 20-30 hours

  3. Authentication Migration Required
     • Google OAuth with Firebase Auth
     • Anonymous login also Firebase-based
     • Token management entirely Firebase
     • Must migrate to Windows Auth or ASP.NET Core Identity
     • Effort: 15-25 hours

🟠 HIGH RISKS:

  4. Firestore Queries Must Be Replaced
     • 8+ Firestore functions (getDocs, getDoc, addDoc, updateDoc, etc.)
     • All must be converted to REST API calls
     • Effort: 20-30 hours

  5. Offline Logic Redesign
     • IndexedDB persistence automatic via Firebase
     • LocalStorage fallback for offline mode
     • Need new sync logic without Firebase
     • Could implement Service Worker + offline queue
     • Effort: 15-25 hours

  6. SQLite Multi-User Support (5-20 concurrent users)
     • SQLite Single-Writer limitation
     • May need row-level locking strategy
     • Alternative: Consider PostgreSQL
     • Effort: 10-20 hours

  7. Security Improvements Required
     • Current Firestore Rules too permissive
     • Need server-side permission validation
     • No field-level validation
     • Effort: 15-25 hours

🟡 MEDIUM RISKS:

  8. Drag-and-Drop Testing
     • Must be thoroughly tested after API migration
     • Visual feedback components affected
     • Effort: 5-10 hours

  9. Theme Persistence Strategy
     • Currently localStorage-based
     • Decision: Keep local-only or persist server-side?
     • Effort: 2-5 hours

  10. Performance with Monolithic File
      • 135 KB file size acceptable now, but...
      • Code splitting may be needed for future growth
      • Effort: 10-20 hours (if required)

DECISION 1: Authentication Method
────────────────────────────────────────────────────────────────────────────

  OPTION A: Windows Authentication (Active Directory)
    Pros:
      ✓ Seamless SSO with Windows login
      ✓ No separate password management
      ✓ Security best practice for enterprise
      ✓ Automatic user identification
    Cons:
      ✗ Requires Windows domain
      ✗ Limited to Windows environment

  OPTION B: ASP.NET Core Identity (Built-in Users)
    Pros:
      ✓ Full user management in application
      ✓ Password reset, 2FA support
      ✓ Works across platforms
      ✓ Flexible for custom requirements
    Cons:
      ✗ Must manage user database
      ✗ Password reset infrastructure needed

  OPTION C: OAuth/OIDC Integration
    Pros:
      ✓ Delegated authentication
      ✓ Support multiple providers
    Cons:
      ✗ More complex to implement
      ✗ Dependency on external services

DECISION 3: Multi-User Concurrency Strategy
────────────────────────────────────────────────────────────────────────────

  OPTION A: SQLite with Locking
    Pros:
      ✓ No additional infrastructure
      ✓ Lightweight, minimal configuration
      ✓ Cost-effective
    Cons:
      ✗ Single-writer limitation
      ✗ Possible contention at 5-20 concurrent users
      ✗ Less robust for high load

  OPTION B: PostgreSQL
    Pros:
      ✓ Multi-user optimized
      ✓ Better concurrent access handling
      ✓ More scalable
      ✓ Professional-grade reliability
    Cons:
      ✗ Additional installation required
      ✗ Higher resource overhead
      ✗ More complex administration

  ➜ PLEASE CHOOSE: A (SQLite) / B (PostgreSQL)

────────────────────────────────────────────────────────────────────────────

DECISION 4: Offline-Sync Support
────────────────────────────────────────────────────────────────────────────

  OPTION A: YES - Implement Offline Queue + Auto-Sync
    Pros:
      ✓ Users can work offline
      ✓ Changes sync automatically when online
      ✓ Better user experience with weak connection
      ✓ Professional-grade feature
    Cons:
      ✗ More complex implementation
      ✗ Conflict resolution logic needed
      ✗ Additional testing required
      ~ Estimated effort: +15-20 hours

  OPTION B: NO - Online-Only (with Browser Cache)
    Pros:
      ✓ Simpler implementation
      ✓ No sync complexity
      ✓ Less code to maintain
    Cons:
      ✗ No offline work capability
      ✗ Poor UX with connectivity issues
      ✗ Users lose work if disconnected

  ➜ PLEASE CHOOSE: A (With Sync) / B (Online-Only)

────────────────────────────────────────────────────────────────────────────

DECISION 5: API Versioning Strategy
────────────────────────────────────────────────────────────────────────────

  OPTION A: URL-Based (/api/v1/tasks)
    Pros:
      ✓ Explicit and visible in URLs
      ✓ Easy to understand and debug
      ✓ Clear separation of versions
    Cons:
      ✗ Slightly less RESTful
      ✗ Duplicate routes for versions

  OPTION B: Header-Based (Accept: application/vnd.prkanban.v1+json)
    Pros:
      ✓ Follows REST standards
      ✓ Clean URLs without version
      ✓ Professional approach
    Cons:
      ✗ Less obvious to developers
      ✗ Harder to debug
      ✗ Requires custom Accept header

  ➜ PLEASE CHOOSE: A (URL-Based) / B (Header-Based)
